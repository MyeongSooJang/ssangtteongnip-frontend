# PR 양식과 머지 절차

PR을 만들거나 머지할 때만 읽는다. 커밋·브랜치 규칙은 `SKILL.md`에 있다.

## PR 양식

### 제목
커밋과 같은 형식 `type(scope): 한국어 설명`을 쓴다. 70자 이내. merge commit으로 머지하면 이 제목이 main의 머지 커밋 메시지에 남아 PR 단위를 구분하는 기준이 된다.

### 본문
아래 섹션을 순서대로 포함한다. 해당 없는 섹션은 "해당 없음"으로 적거나 생략한다. 섹션마다 리뷰어가 읽을 만큼만 간결하게 쓴다.

```markdown
## 요약
<!-- 이 PR의 목적 한 문장. 관련 이슈가 있으면 Closes #번호 -->

## 배경
<!-- 왜 이 변경이 필요했는지, 어떤 문제나 요구가 있었는지 -->

## 변경 내용
<!-- 접근 방식과 설계 결정, 버린 대안. 파일 나열은 쓰지 않는다 -->

## 리뷰 포인트
<!-- 먼저 볼 파일, 위험한 부분, 미확인 사항 -->

## 테스트
- [x] 자동화 테스트: (실행한 명령과 결과, 예: `npx vitest run` 몇 개 통과)
- [x] 타입체크: `npx tsc -b` 결과
- [x] 직접 실행 확인: (가짜 데이터 화면을 직접 띄워 확인한 내용. 해당 없으면 줄을 삭제)

## 화면
<!-- 화면이 바뀐 PR만. CLAUDE.md의 "화면이 바뀌는 PR에는 스크린샷을 첨부한다" 규칙을 따른다. 없으면 생략 -->
```

### 작성 규칙
- 본문에 `🤖 Generated with Claude Code` 등 AI 서명을 넣지 않는다.
- "코드 리뷰 후속 작업" 체크리스트 섹션을 넣지 않는다.
- "변경 내용"에는 코드를 보면 알 수 있는 파일·함수 나열을 쓰지 않고, 왜 그렇게 짰는지(접근 방식·설계 결정)를 쓴다.
- 백엔드 API 계약 변경에 의존하는 PR, 환경변수 추가, 사용자 브라우저에 저장된 값(localStorage 키 등)의 변경으로 재로그인 같은 영향이 생기는 경우, Breaking Change는 "변경 내용"에 적고 제목에 `!`를 붙인다. 별도 섹션을 두지 않으므로 빠뜨리지 않는다.
- 프론트가 새 백엔드 API를 쓰는 PR은 백엔드가 먼저 배포되어야 하므로 머지 순서를 "변경 내용"에 적는다.
- 인증·권한 처리, 토큰 저장, 인증 없이 열리는 경로를 바꿨다면 보안 영향을 리뷰 포인트에 적는다.
- 테스트 결과는 **실제로 실행한 값**만 쓴다. 실행하지 않은 항목을 체크하지 않는다. 테스트 개수도 실행 결과 그대로 쓴다.
- "수동 확인" 체크박스처럼 사람이 나중에 확인할 항목을 PR에 남기지 않는다. 화면은 PR을 만들기 전에 직접 띄워 확인하고, 확인한 결과만 "직접 실행 확인"에 적는다. 확인하지 못한 것(백엔드 연동, 실제 배포 서버 등)은 체크박스로 두지 말고 리뷰 포인트에 "미확인: 이유" 문장으로 적는다. 화면을 직접 보지 못했으면 봤다고 쓰지 않는다.
- PR 본문은 **파일로 작성하고 `gh pr create --body-file`로 올린다.** 셸 문자열에 직접 넣으면 백틱·`$`·`|`가 깨진다. 올린 뒤 `gh pr view <번호> --json body -q .body`로 표와 링크가 그대로인지 확인한다.

### 머지 전 확인
사용자가 머지를 지시하거나 확인했고 아래 항목이 모두 충족되면 `gh pr merge <번호> --merge --delete-branch`로 머지한다.

1. PR이 `main` 대상이고 충돌이 없는가 (`mergeable`)
2. 테스트 섹션의 항목이 실제로 실행되어 통과했는가 (이번 세션에서 실행한 결과 기준)
3. CI 체크가 설정되어 있다면 통과했는가
4. team 모드: 리뷰어 승인(`reviewDecision`이 `APPROVED`)이 있는가
5. `mock-preview.*`가 남아 있지 않고 미리보기 개발 서버(127.0.0.1:5173)가 꺼져 있는가 (`git status`로 확인. 훅도 확인한다)

### 머지 뒤 정리
머지가 끝나면 브랜치가 남지 않았는지 확인하고 정리한다. 별도 지시를 기다리지 않는다.

- `gh pr view <번호> --json state`가 `MERGED`인지 확인한다. 아니면 어떤 브랜치도 지우지 않는다.
- 원격: `gh api repos/<소유자>/<저장소>/branches -q '.[].name'`에 그 브랜치가 남아 있으면 `git push origin --delete <브랜치>`로 지운다.
- 로컬: `main`으로 옮겨 `git pull --ff-only` 후 `git branch -d <브랜치>`로 지운다. `-d`는 머지되지 않은 브랜치를 거부하므로 `-D`는 쓰지 않는다.
- 결과(삭제한 브랜치, 남은 브랜치)를 마무리 보고에 한 줄로 적는다.
