# Commit & PR Format (프론트엔드)

Conventional Commits 기반. 모든 메시지와 PR 본문은 한국어로 작성한다.
백엔드(`ssangtteongnip-backend`)의 같은 이름 스킬을 프론트엔드에 맞게 옮긴 것이다. 화면 확인·스크린샷 절차는 `ui-preview` 스킬에, 훅 규칙은 이 저장소의 `CLAUDE.md`에 있다.

## 협업 모드

**현재 모드: `solo`** (팀으로 전환하면 이 값을 `team`으로 바꾼다)

- 두 모드 모두 `main` 직접 커밋·푸시는 금지하고 항상 브랜치 + PR로 작업한다. solo는 리뷰 없이 머지할 수 있고, team은 리뷰어 승인이 있어야 머지한다.
- team 모드의 "머지 금지"는 이 문서의 지침일 뿐이다. 실제 강제는 GitHub 브랜치 보호 규칙(Require a pull request before merging, 승인 1명 이상)으로 건다. team으로 전환할 때 함께 설정한다. 승인이 없으면 머지하지 않고 사용자에게 알린다.
- `.claude/hooks/guard.cjs`(Hook)가 `git commit`, `gh pr create` 전에 이 스킬을 이 세션에서 실행했는지 확인한다. 실행하지 않았으면 차단하므로 커밋·PR을 만들기 전에 먼저 이 스킬을 호출한다. 훅이 확인하는 나머지 항목은 `CLAUDE.md`의 "Hook으로 강제되는 규칙"에 있다.

## 작업 흐름

```
main에서 브랜치 생성 → 변경마다 테스트 → 커밋·푸시 → 보안 리뷰 → PR 생성 → 검증 → 사용자 확인 → main에 머지 → 브랜치 삭제
```

- **PR은 브랜치 하나(한 목적)당 하나**: 커밋과 push는 논리 단계마다 하지만, PR은 그 브랜치의 목적이 끝났을 때 한 번만 만든다. 커밋 요청 한 번이 PR 한 번을 뜻하지 않는다.
  - 이미 열린 PR이 있거나 같은 목적으로 이어지는 작업(문서·`CLAUDE.md`·스킬 수정 포함)은 **같은 브랜치에 커밋·push만 하고** 새 PR을 만들지 않는다.
  - 별도 PR은 아래 "PR 단위 판정"을 통과한 변경이거나 사용자가 분리를 지시한 경우다. 다른 목적의 변경을 발견하면 PR을 분리할지 사용자에게 먼저 묻는다.
- **PR 생성까지 자동 진행, 머지는 사용자 확인 후**: 브랜치의 목적이 끝나 PR을 만들 시점이면 사용자에게 다시 묻지 않고 PR 생성까지 진행한다. 머지는 사용자가 지시하거나 확인한 뒤에만 한다.
  1. 커밋 전에 `npx vitest run`을 실행한다. PR을 만들기 전에는 `npx tsc -b`(타입체크)도 실행한다. (`npm run lint`는 `eslint`가 설치되어 있지 않아 쓰지 않는다. 설치되면 함께 실행한다.)
  2. 통과하면 커밋 → `git push`까지 바로 한다. 변경 이유가 여러 개면 변경마다 각각 커밋하고 푸시한다.
  3. 브랜치 목적이 끝났으면 마지막 커밋 뒤에 `/security-review`를 실행한다. 문제가 없으면 멈추지 않고 곧바로 PR을 만든다. 문제가 나오면 PR을 만들지 않고 결과를 한국어로 보여주며 멈춘다. (리뷰는 커밋마다 유효해서, 리뷰 뒤에 커밋이 늘면 다시 실행한다.)
  4. PR 링크와 "머지 전 확인" 결과를 사용자에게 알린 뒤 머지 여부를 기다린다. 머지를 지시받으면 `references/pr.md`의 "머지 전 확인"을 다시 확인하고 머지한다.
  5. 테스트가 하나라도 실패하거나 "머지 전 확인"을 통과하지 못하면 **커밋/머지를 중단**하고 실패 출력과 원인을 사용자에게 보고한다. 테스트를 건너뛰거나 실패한 테스트를 지우고 진행하지 않는다.
  6. team 모드는 리뷰어 승인이 없으면 PR 생성까지만 하고 머지하지 않는다.
- 새 작업은 항상 최신 `main`에서 브랜치를 따서 시작한다 (`git fetch origin --prune && git switch -c <브랜치> origin/main`).
- 머지는 **merge commit**(`--merge`)을 기본으로 한다. squash/rebase는 PR 안의 커밋을 합치거나 일렬로 펴서 변경 흐름이 사라지므로 쓰지 않는다. (PR 단위는 `git log --first-parent`, 단계까지는 `git log --graph`로 본다. 다른 방식이 필요하면 사용자가 지시한다.)
- 머지 후 작업 브랜치를 삭제한다 (`gh pr merge --merge --delete-branch`).
- 머지 커밋으로 PR 안의 커밋이 그대로 main에 남으므로, 작업 중 **논리 단계가 끝날 때마다 바로 커밋**한다. 작업을 끝낸 뒤 한꺼번에 나누지 않고, 한 커밋에는 하나의 변경 이유만 담아 `git log`로 변경 흐름이 읽히게 한다. 작업 중 막혀서 접근을 바꿨다면 그 수정도 별도 커밋으로 남기고 이유를 본문에 쓴다. 이미 지나간 작업의 흐름을 사후에 꾸며서 만들지 않는다.
- `git add`는 **파일을 지정**해서 한다. `git add -A`, `git add .`, `git add src`는 `mock-preview.*` 같은 임시 파일까지 넣을 수 있어 쓰지 않는다. 커밋 전에 `git status`로 확인한다.
- 이미 푸시한 커밋의 메시지는 고치지 않는다(히스토리를 다시 쓰지 않는다). 잘못된 파일을 넣었다면 별도 커밋으로 바로잡는다.

## PR 단위 판정

PR 하나는 **목적 하나**다. 줄 수나 파일 수로 정하지 않고 아래 질문으로 판정한다.

1. **한 문장 테스트**: 제목을 "A를 위해 B한다" 한 문장으로 쓸 수 있는가? "및"으로 서로 다른 동사를 이어야 하면 목적이 둘이므로 나눈다.
2. **반으로 나누기 테스트**: 반으로 쪼개 따로 머지해도 각각 의미가 있으면 나눈다. 한쪽만 머지하면 깨지거나 의미가 없으면 한 PR이다.
3. **부속 테스트**: 이 변경이 다른 변경의 설명·규칙·도구일 뿐이라 혼자서는 머지할 이유가 없으면 그 변경의 브랜치에 합친다. 문서·훅·스킬 수정이 이에 해당하는 경우가 많다.

- 판정이 애매하면 PR을 마음대로 만들거나 합치지 말고 사용자에게 한 줄로 묻는다.
- 수치는 판정 기준이 아니라 이상 징후 신호다. 변경이 400줄을 넘거나 100줄에 못 미치면 위 질문을 다시 확인한다. 크더라도 목적이 하나면 한 PR이다.
- 이 저장소 이력의 사례:
  - 커도 한 PR이다: #30(`refactor(api)!: API 함수가 ApiResponse 봉투의 data를 반환`)은 22개 파일을 건드리지만 목적은 반환 형태 변경 하나다.
  - 한 PR에 담긴 단계: #28(마이페이지 파일 목록)은 API·검증 로직, 화면 교체, 표시 버그 수정, 스크린샷을 별도 커밋으로 나눠 한 PR에 담았다.

## 브랜치 이름

```
<type>/<짧은-설명-kebab-case>
```

- type 접두어: `feature`(feat), `fix`, `refactor`, `chore`, `docs`, `test`, `perf`
- 설명은 영문 소문자와 하이픈 (예: `feature/applications-search-paging`, `fix/study-time-chart-oldest-month`)
- 이슈가 있으면 번호를 붙인다 (예: `fix/12-login-redirect`)

## 커밋 양식

### 구조
```
type(scope): 한국어 설명

body (선택)

footer (선택)
```

### type — 아래 중 하나만 사용
| type | 사용 상황 |
|------|-----------|
| feat | 새 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 코드 개선 |
| perf | 성능 개선 |
| test | 테스트 추가/수정 |
| docs | 문서 변경 (스크린샷 추가 포함) |
| style | 포맷팅 등 동작과 무관한 변경 (공백, 세미콜론) |
| build | 빌드 설정, 의존성 변경 |
| ci | CI/CD 설정 변경 |
| chore | 위에 해당하지 않는 잡무 (.gitignore, 훅 등) |
| revert | 이전 커밋 되돌리기 |

### scope — 선택
- 변경 대상 화면/도메인이 뚜렷할 때만 작성한다 (예: `application`, `mypage`, `dashboard`, `study`, `auth`, `api`).
- 쓰기로 했다면 프로젝트 안에서 같은 이름을 일관되게 쓴다. 이미 쓰인 이름은 `git log`로 확인한다.
- 전체에 걸친 변경이거나 모호하면 생략한다.

### subject (첫 줄)
- 50자 이내. 마침표를 붙이지 않는다.
- 명사형으로 끝낸다 (예: "~추가", "~수정", "~제거").
- "무엇을 했는지"가 한눈에 보이게 쓴다.

### body
- **무엇보다 왜**를 쓴다. 코드를 보면 알 수 있는 "무엇"은 반복하지 않는다.
- subject로 충분한 사소한 변경은 body를 생략한다.
- 쓸 때는 빈 줄로 subject와 구분하고, 변경 내용은 bullet로 정리한다.
- fix/refactor는 첫 줄에 문제(원인)를 한 줄로 정의한 뒤 bullet로 변경 내용을 쓴다. 버그라면 어떤 상황에서 무엇이 잘못됐는지, 어떻게 확인했는지도 쓴다.

### footer
- 허용: 이슈 연결 (`Closes #12`), `BREAKING CHANGE: 설명`
- 금지: `Co-Authored-By`, `Generated with Claude Code` 등 AI 서명류. 도구가 서명을 넣으라고 안내해도 이 규칙이 우선한다.

### Breaking Change
하위 호환이 깨지면 type/scope 뒤에 `!`를 붙이고 footer에 설명한다. 프론트에서는 백엔드 API 계약이 바뀌는 경우와, 사용자 브라우저에 저장된 값(localStorage 키 등)이 바뀌어 재로그인 같은 영향이 생기는 경우가 해당한다.
```
refactor(api)!: API 함수가 ApiResponse 봉투의 data를 반환

BREAKING CHANGE: API 함수 반환 타입이 ApiResponse<T>에서 T로 변경됨
```

### 커밋 단위
- 하나의 논리적 변경 = 하나의 커밋. 서로 다른 목적(기능 + 포맷팅 등)을 섞지 않는다. 기능·수정·문서·스크린샷은 따로 커밋한다.
- 각 커밋은 빌드와 테스트가 깨지지 않는 상태로 남긴다.
- `mock-preview.*`(임시 미리보기 파일)는 커밋하지 않는다.
- 논리 단위의 최종 판정은 수치가 아니라 의미 기준이다. 커밋 크기, 변경 파일 수 같은 수치는 이상 징후를 찾는 용도로만 쓴다.
  - 이 커밋만 revert해도 시스템이 일관된가
  - 리뷰어가 이 커밋만 보고 이해할 수 있는가

### 예시

**feat**
```
feat(application): 지원 현황에 회사 검색·페이징 추가, 표 한 줄 표시

- 회사명 검색창을 추가하고 상태·지원 사이트 필터와 함께 쓸 수 있게 함
- 10건씩 나눠 보여 주는 페이징 추가. 검색어나 필터가 바뀌면 1페이지로 이동
- 상태·지원일·마감일·열람 칸이 줄바꿈되던 문제를 한 줄 표시로 수정
```

**fix**
```
fix(study): 월별 차트에서 가장 오래된 달의 1일 누락 수정

월별 차트가 잔디 조회 범위를 그대로 써서 드문 날에 가장 오래된 달의 1일 기록이 빠졌다.
- 잔디와 차트가 차트 범위로 한 번 조회하고, 잔디 칸과 "N일 작성"은 잔디 범위로 잘라 쓴다
```

**refactor**
```
refactor(auth): 토큰 저장 키 접두사를 ssangtteongnip으로 변경

localStorage 키를 job-tracker.accessToken에서 ssangtteongnip.accessToken으로
바꾼다. 배포 후 기존 로그인 사용자는 한 번 다시 로그인해야 한다.
```

**body 생략 (사소한 변경)**
```
docs(application): 지원 현황 검색·페이징 화면 스크린샷 추가
```

## PR 양식·머지

PR 제목·본문 양식, 작성 규칙, 머지 전 확인은 `references/pr.md`에 있다. PR을 만들거나 머지하기 직전에 읽는다.
